# Battle Architecture Rules

Updated: 2026-07-25.

이 문서는 전투 서버를 확장하거나 리팩터링할 때 사용하는 **구조 결정의 기준점**이다. 새 기능을 구현할 때는 먼저 이 문서의 책임 경계를 따른다. 경계가 애매하면 `BattleRoom`에 우선 넣지 말고, 아래 순서로 소속을 판단한다.

1. 모든 폰이 공유하는 규칙인가? → 공용 서비스
2. 특정 캐릭터/무기만의 판단·상태·형상인가? → 해당 `BattlePawn` 하위 클래스
3. 조정 가능한 수치·효과 조합인가? → CSV
4. 전투 상태, 패킷, 서비스 호출 순서를 조율하는가? → `BattleRoom`

## 목표 구조

```text
BattleRoom
 ├─ BattlePawn hierarchy       : 캐릭터 전용 판단과 상태
 ├─ Battle*Service             : 재사용 가능한 전투 규칙
 ├─ BattleEffectExecutor       : CSV 효과 원시 기능 실행
 └─ BattleSkillResolver        : 상태/수치 기반 수정자 해석

Data/*.csv                     : 스킬 수치와 효과 조합
```

## 1. BattleRoom: 전투 조율자

`BattleRoom`은 서버 권위 전투의 진입점이며, **규칙 자체의 소유자**가 아니다.

### 맡는 일

- 클라이언트 패킷 수신, 소유권·턴·생존 여부 검증
- `BattleState` 보관, 턴 전환, 승패 처리
- 서비스와 캐릭터 훅 호출 순서 조율
- 결과를 `S_BATTLE_*` 패킷과 pawn/tile delta로 직렬화
- 전장 상태 조회 함수 제공(타일, 점유, 폰 검색)

### 넣지 않는 일

- `ALEN_SPEAR`, `SUEN_AXE` 같은 캐릭터명/스킬명 분기
- 개별 캐릭터의 범위, 장비 상태, 특수 발동 조건
- 범용 계산식(이동거리, 밀치기, 육각 거리, ZOC 등)

`BattleRoom`에 캐릭터명 또는 특정 스킬 키가 새로 등장하면, 먼저 하위 클래스·CSV·서비스 중 어디로 옮길지 검토한다.

## 2. BattlePawn 계층: 캐릭터 고유 행동

```text
BattlePawn
├─ Beige
│  ├─ BeigeIce
│  └─ BeigeFire
├─ Suen
│  └─ SuenAxe
└─ Alen
   └─ AlenSpear
```

하위 클래스는 해당 계열만 이해해야 하는 전용 규칙을 맡는다.

- 고유 타겟 영역: `AlenSpear::ResolveTargetArea(LINE_2)`
- 고유 상태 전환: `SuenAxe`의 AxeOn/AxeOff 및 도끼 회수
- 고유 사용 가능 조건: 장비 소유 여부, 토글 상태, 특수 자원 조건
- 고유 상호작용: 오직 해당 캐릭터에만 적용되는 장비·타일·버프 반응

하위 클래스에는 일반 피해 산식, 일반 이동 검증, 공용 상태이상 처리를 복제하지 않는다.

## 3. 공용 서비스: 재사용 가능한 규칙

공용 서비스는 캐릭터명을 알지 못하고, 폰의 상태·프로필·콜백만으로 동작해야 한다.

| 서비스 | 책임 |
| --- | --- |
| `BattleSpatialService` | 축좌표 거리, 방향, 바라보는 방향, 백어택 판정 |
| `BattleMovementService` | 상태 수정자를 반영한 최종 이동거리 계산. 소수 이동력은 버림. |
| `BattleDisplacementService` | 밀치기 방향, 장애물·점유 충돌, 강제 이동 결과 |
| `BattleTurnService` | 턴 큐 구성·순환·사망 폰 건너뛰기 |
| `BattleZocService` | 역할/프로필 기반 ZOC 범위·반응 조건 |
| `BattleSkillExecutionService` | 대상/범위 확장, 효과 실행 요청, 결과 수집 |
| `BattleEffectExecutor` | 피해, 상태, 자원, 장벽, 이동 수정자 등 EffectKey 원시 기능 실행 |

서비스는 새 캐릭터를 추가해도 수정되지 않는 것을 목표로 한다. 새 캐릭터 때문에 서비스에 캐릭터 분기가 필요해지면, 먼저 일반화된 입력값·프로필·훅으로 표현할 수 있는지 검토한다.

## 4. CSV: 조정 가능한 설계 데이터

CSV는 ‘무엇을, 얼마나’ 할지를 정의한다. 코드가 CSV 값을 읽어 공용 원시 기능으로 실행한다.

- `PawnTemplate.csv`: 역할, 기본 스탯, 이동력
- `BattleSkill.csv`: 슬롯, 대상 유형, 사거리, 효과 그룹
- `BattleSkillEffect.csv`: 효과의 순서·트리거·대상
- `BattleSkillEffectParam.csv`: 피해 계수, 지속 턴, 확률, 수정자 수치
- `BattleZoc.csv`: 역할별 ZOC 프로필

예: 알렌 창 궁극기의 ‘모든 아군 이동력 1.5배, 2턴’은 `ALEN_SPEAR_CHARGE_COMMAND` 효과 데이터다. 공용 `BattleMovementService`가 그 상태 수정자를 반영해 최종 이동거리만 계산한다. 기본 3칸은 `floor(3 × 1.5) = 4`칸이다.

## 5. 구현 순서 체크리스트

새 전투 기능을 추가할 때 아래 순서로 작업한다.

1. 게임 규칙과 대상/턴/반응을 먼저 명세한다.
2. 수치·지속시간·사거리·효과 조합을 CSV에 정의한다.
3. 기존 `EffectKey`와 서비스만으로 가능한지 확인한다.
4. 불가능하면, 공용 원시 기능은 서비스/이펙트 실행기에 추가한다.
5. 캐릭터 전용 판단만 해당 하위 클래스에 추가한다.
6. `BattleRoom`에서는 검증·호출·델타 전송만 연결한다.
7. 서버 로그와 클라이언트 delta/표시 요구사항을 확인한다.
8. 빌드 및 실제 전투 시나리오로 검증한다.

## 6. 금지 패턴

- `BattleRoom`에 캐릭터별 `if (pawnClass == ...)`를 누적하지 않는다.
- 같은 계산식을 캐릭터 클래스마다 복사하지 않는다.
- 조정 대상 수치를 C++ 상수로 고정하지 않는다.
- 클라이언트 판정 결과를 서버의 최종 전투 결과로 신뢰하지 않는다.
- CSV에 넣기 어렵다는 이유만으로 모든 규칙을 거대한 효과 실행기 하나에 몰아넣지 않는다.

## 7. Codex 작업 규칙

향후 Codex는 전투 변경 전 이 문서를 기준으로 소속을 먼저 판단하고, 판단 근거를 짧게 공유한다. 구조를 바꾸는 작업에서는 관련 옵시디언 노트와 클라이언트 전달 사항도 함께 갱신한다.
